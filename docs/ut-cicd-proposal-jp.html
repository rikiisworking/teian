2 現状フローで発生しやすいコスト

リードタイムが長い

testcases.json生成 → アップロード → SQL作成 → 実行待ちが直列に続きます。

ヒューマンエラー

手動アップロード、スキーマ変更、実行順のミスが結果に混ざります。

環境が分散

参考資料・ローカル設定・実行環境が人ごとに違い、再現が難しくなります。

確認作業が特定の工程に集中しやすい

SQL作成とレポート確認が特定の工程に集まり、前後の作業が待ちになりやすくなります。

5 変換ロジックを中心に

Glueスクリプトは一般に Load → Transform → Save の構造です。Load/SaveはDBやS3への接続、認証情報、ネットワーク環境に依存するため、CI環境でそのまま毎回検証しようとすると準備コストが高く、実行も不安定になりがちです。

一方でTransform部分は「入力DF → 出力DF」という純粋な処理として切り出せます。実際のDB接続を用意しなくても、あらかじめ用意したテストデータだけで高速かつ再現性高くテストできるため、UTの対象をTransformに絞ることでCI/CDとの相性が良くなり、テスト自体もシンプルになります。

input DF  →  transform  →  output DF
flowchart LR subgraph Now["現在のスクリプト"] L[Load from DB/S3] --> T[Transform] --> S[Save to DB/S3] end subgraph Next["UT範囲"] I[input DF] --> X[transformモジュール] --> O[output DF検証] end T -.-> X

モジュール化できれば、同じ単位をつなげてIT（パイプライン）も「DF変換の連続」として簡素化できる余地があります。

7 リスクと注意点

ブランチ運用の前提

ブランチ運用を揃えることが前提になります。

構築期間

環境構築には1-2週間程度かかる見込みです。

IT検証は追加工数が必要

実データを用いたIT向けの検証基盤を構築するには、別途工数がかかります。
