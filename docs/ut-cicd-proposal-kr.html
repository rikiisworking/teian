2 현재 프로세스에서 발생하는 부담

긴 리드타임

자료 공유 → 로컬 설정 → SQL 작성 → 실행 대기가 직렬로 이어집니다.

휴먼에러

수동 업로드, 스키마 변경, 실행 순서 실수가 결과에 섞여 들어갑니다.

환경 분산

참고 자료·로컬 설정·실행 환경이 사람마다 달라 재현이 어렵습니다.

리더 병목

SQL 작성과 리포트가 리더에게 몰려 팀 전체가 대기하게 됩니다.

3 왜 CI/CD가 이 문제에 맞는가

flowchart LR P[코드 Push / PR] --> C[CI가 변경분 UT 실행] C --> R[합격 여부 즉시 표시] R --> M[리뷰 / 머지] R --> L[로그 = 리포트 원본]
검증 시점이 앞당겨짐

리더 SQL을 기다리지 않고, 개발자가 코드를 올린 시점에 해당 변경분만 테스트합니다.

동일한 환경 공유

로컬 환경 차이가 아니라, CI 러너 위에서 동일한 절차를 반복 실행합니다.

로그로 보고서 작성

리더는 케이스를 재실행하는 대신, 결과 로그를 근거로 리포트를 작성할 수 있습니다.

※ 그림 속 GitHub Actions는 하나의 예시입니다. 기존 Git 운용 방식에 맞춰 다른 CI 서비스로 대체할 수 있습니다.

5 변환 로직을 중심으로

Glue 스크립트는 일반적으로 Load → Transform → Save 구조입니다. Load/Save는 DB나 S3 접속, 인증 정보, 네트워크 환경에 의존하기 때문에, CI 환경에서 그대로 매번 검증하려고 하면 준비 비용이 높고 실행도 불안정해지기 쉽습니다.

반면 Transform 부분은 "입력 DF → 출력 DF"라는 순수한 처리로 분리할 수 있습니다. 실제 DB 연결을 준비하지 않아도 미리 만들어둔 테스트 데이터만으로 빠르고 재현성 있게 테스트할 수 있기 때문에, UT의 대상을 Transform으로 좁히면 CI/CD와의 궁합이 좋아지고 테스트 자체도 단순해집니다.

input DF  →  transform  →  output DF
flowchart LR subgraph Now["현재 스크립트"] L[Load from DB/S3] --> T[Transform] --> S[Save to DB/S3] end subgraph Next["UT 범위"] I[input DF] --> X[transform 모듈] --> O[output DF 검증] end T -.-> X

모듈화가 이루어지면, 동일한 단위를 이어 붙여 IT(파이프라인)도 "DF 변환의 연속"으로 단순화할 여지가 있습니다.
